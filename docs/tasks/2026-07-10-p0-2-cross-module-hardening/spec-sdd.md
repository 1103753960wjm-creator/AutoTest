# Spec/SDD：各部分 P0.2 跨模块硬化

## 1. 背景

- 当前用户要求：进入各部分的 P0.2。
- 这里的“各部分 P0.2”按 `docs/planning/full-stack-optimization-implementation-plan.md` 理解，覆盖前端 UI、前端代码、后端架构、接口、后端代码、注释与文档六个 P0.2。
- 本轮不是直接开始改代码。P0.2 横跨前端、后端、接口错误契约、生产配置、敏感信息和实时连接，按仓库规则属于高风险跨模块任务，必须先完成 `Spec/SDD`，等待用户确认后再进入 `TDD`。
- P0.1 代码和文档已经收尾，但真实浏览器回归仍有未验证项，包括真实浏览器主流程、真实 App 报告文件 200、真实无权限对象 403、浏览器 EventSource 凭据行为、接口自动化阶段 A 人工回归。

## 2. 当前生效规则

- 生效流程：`Spec/SDD -> TDD -> Execution -> VDD`。
- 本轮自治等级：L0 到 L2 之间。
  - 当前 `Spec/SDD` 阶段属于 L0，只能审计、设计方案、写清范围并等待确认。
  - 用户确认 `Spec/SDD` 和后续 `TDD` 后，Execution 可按 L2 在确认范围内推进。
- 是否允许受控 Loop：当前不允许进入 Loop；如后续实现阶段验证失败，再单独写 L3 Loop 合同。
- 原生参考代码：只读参考，不修改。
- 重要红线：
  - 前端请求必须走 `frontend/src/api/* -> frontend/src/utils/api.js`。
  - 后端接口必须走 `backend/urls.py -> apps/<module>/urls.py -> views -> serializers/services/models`。
  - 生产配置和敏感信息不能为了方便启动而放宽。
  - 不能为通过验证降低权限、屏蔽错误或伪造成功。

## 3. 本轮目标

### 3.1 前端 UI P0.2：清理生产环境调试视觉入口

- 清理生产环境不该出现的调试对象、调试块、临时标识和业务调试日志。
- 涉及页面按计划优先看：
  - `frontend/src/views/ui-automation/elements/ElementManagerEnhanced.vue`
  - `frontend/src/views/api-testing/InterfaceManagement.vue`
  - `frontend/src/views/app-automation/test-cases/SceneBuilder.vue`
  - `frontend/src/views/auth/Login.vue`
  - `frontend/src/router/index.js`

### 3.2 前端代码 P0.2：实时连接统一封装

- 把 SSE / WebSocket 的连接、关闭、错误、有限重连、离开页面自动断开收口到统一 composable。
- 优先新增或补齐：
  - `frontend/src/composables/useEventSource.js`
  - `frontend/src/composables/useWebSocket.js`
- 优先改造点：
  - `frontend/src/composables/useGenerationTaskTracking.js`
  - `frontend/src/views/requirement-analysis/RequirementAnalysisView.vue`
  - App 自动化测试用例列表中实时连接相关代码
  - 接口测试工作区中 WebSocket / SSE 相关代码

### 3.3 后端架构 P0.2：生产配置硬化复核

- 复核生产配置硬化是否已经完整覆盖计划要求。
- 当前项目记忆显示已经完成过一轮：
  - `DEBUG` 严格布尔解析。
  - 生产环境必须显式配置 `ALLOWED_HOSTS`、`CORS_ALLOWED_ORIGINS`。
  - 禁止生产环境 `ALLOWED_HOSTS=*`。
  - 禁止生产环境 `DISABLE_CSRF_FOR_API=True`。
  - `.env.example` 已补充配置说明。
- 本轮不盲目重写配置，只做缺口复核和补齐：
  - `SECRET_KEY` 是否仍可能使用开发默认值。
  - Redis / DB / Celery 关键配置缺失时是否有清晰失败。
  - `.env.example` 和部署说明是否足够让运维按步骤配置。

### 3.4 接口 P0.2：接口错误结构统一

- 让前端能用统一方式读取错误原因，减少每个页面按接口特判。
- 本轮不能全仓强行改成功响应结构。
- 错误结构统一优先覆盖错误响应，不动正常成功响应。
- 需要先定义最小错误格式，例如：
  - `code`：机器可读错误码。
  - `message`：给用户看的错误原因。
  - `details`：字段级错误或补充信息。
  - `request_id`：后续追踪用，若当前日志体系不足可先预留。
- 权限错误、参数校验错误、业务错误、外部服务错误要有明确分类。

### 3.5 后端代码 P0.2：敏感信息保护

- 避免日志、响应、异常信息泄露：
  - API Key
  - token
  - Authorization
  - Cookie
  - 密码
  - 请求头原文
  - AI 模型配置密钥
- 优先补一套敏感字段清单和脱敏 helper。
- 配置类接口、测试连接接口、异常日志、调试日志必须重点检查。

### 3.6 注释与文档 P0.2：核心配置补说明

- 给生产配置和敏感配置补清楚说明。
- 优先检查：
  - `.env.example`
  - `backend/settings.py`
  - 已有部署 / 运维说明文档
- 文档必须写清：
  - 哪些配置生产必填。
  - 哪些默认值只能开发用。
  - 配错后会发生什么。
  - 哪些字段属于敏感信息，不能提交和截图外传。

## 7. 实施顺序建议

### 第一批：低契约风险和已完成项复核

1. 后端架构 P0.2：生产配置硬化复核。
2. 注释与文档 P0.2：核心配置补说明。
3. 前端 UI P0.2：生产调试入口和调试日志清理。
4. 后端代码 P0.2：敏感字段清单和脱敏工具最小闭环。

原因：这些能提升上线安全性，但相对不需要立刻改动接口成功结构。

### 第二批：实时连接统一封装

1. 先封装 `useEventSource`。
2. 再封装 `useWebSocket`。
3. 每次只改一个真实页面入口，确保离开页面关闭连接、认证失败提示、有限重连都可验证。

原因：实时连接和浏览器凭据行为正好也是 P0.1 未验证项，适合和回归一起补。

### 第三批：接口错误结构统一

1. 先写错误结构规范和兼容策略。
2. 再做后端最小统一异常处理或局部 helper。
3. 前端先做统一错误解析工具，不强迫所有页面一次性改完。
4. 选 2 到 3 个高频接口做试点，验证没问题再扩大。

原因：接口错误结构属于契约变化，一次性全仓改风险过高。

## 8. 风险点

- P0.1 回归未完全执行，进入 P0.2 Execution 后如果出现页面问题，可能难区分是 P0.1 遗留还是 P0.2 新增。
- 接口错误结构统一如果做成全局异常处理，可能改变大量页面对错误的解析方式。
- 实时连接封装如果处理不好，会导致生成进度、执行日志、接口调试等页面连接不关闭、重复订阅或断线不恢复。
- 敏感信息脱敏如果只做响应体不做日志，仍可能在后端日志泄露。
- 生产配置硬化如果验证方式不清楚，可能误伤本地开发启动。
- 清理调试入口如果过度删除，可能影响开发环境排障能力。

## 9. 回退与止损

- 前端调试入口清理：可按文件局部回退，或把仅开发环境可见的诊断能力恢复到 `import.meta.env.DEV` 判断内。
- 实时连接封装：保留旧页面调用方式直到新 composable 验证通过；每次只迁一个页面，失败时回退该页面接入。
- 生产配置硬化：如果误伤本地开发启动，应回退具体校验条件，不回退生产安全原则。
- 接口错误结构：先以兼容工具和试点接口推进；如页面误解析，优先回退试点接口或前端解析工具，不做全仓回退。
- 敏感信息保护：脱敏 helper 如影响正常展示，应只放宽展示字段，不回退日志脱敏。

## 10. 验收标准

- 生产构建后核心页面控制台无业务调试日志、token、用户敏感信息和临时调试对象。
- 页面离开后 SSE / WebSocket 能关闭；网络断开后只做有限重连；认证失败能明确提示。
- 生产配置缺失或非法时，后端启动失败并给出明确错误；本地开发配置仍能正常启动。
- API Key、token、Authorization、Cookie、密码等不会在接口响应和日志中明文出现。
- 前端能通过统一工具读取常见错误信息，不需要每个页面按接口特判。
- `.env.example` 和相关配置说明足够让运维知道哪些配置生产必填、哪些默认值不能用于生产。
- `npm run build` 通过。
- 后端受影响文件 `py_compile` 或 `manage.py check` 通过。
- 高风险链路至少有一条主流程和一条异常流程验证。

## 11. 最低验证目标

- 目标验证等级：至少 V2，关键链路争取 V3。
- 前端最低验证：
  - `cd frontend && cmd /c npm run build`
  - 静态扫描生产调试日志和 `window.*DEBUG*` 业务对象
  - 浏览器验证一个 SSE 页面和一个 WebSocket 页面
- 后端最低验证：
  - 受影响 Python 文件 `py_compile`
  - 开发配置 `manage.py check`
  - 生产缺失配置 / 非法配置的失败验证
  - 脱敏响应和脱敏日志抽样验证
- 接口最低验证：
  - 401/403 权限错误
  - 400 参数校验错误
  - 业务错误
  - 外部服务或模拟超时错误

## 12. 已确认结论

1. 本轮 P0.2 按“三批顺序”推进：先做生产配置复核、配置文档、生产调试入口清理和敏感信息保护；再做实时连接统一封装；最后做接口错误结构试点。
2. P0.1 / 阶段 A 真实浏览器回归作为进入 P0.2 Execution 前的硬闸门。没有跑完这轮回归前，不进入正式改代码。
3. 接口错误结构统一采用保守方案：先试点，保留成功响应结构不变，优先统一错误响应和前端错误解析。
4. 实时连接封装第一批先迁需求分析生成进度 SSE。该入口验证稳定后，再迁 App 自动化和接口测试工作区中的 WebSocket / SSE；后续迁移顺序在 TDD 和 VDD 中继续明确。
5. 敏感信息保护优先覆盖 AI 配置、登录认证、请求头和异常日志，不做全仓所有业务字段脱敏。
