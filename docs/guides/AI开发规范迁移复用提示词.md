# AI 开发规范迁移复用提示词

## 1. 文档用途

这份文档用于把当前项目的 AI 协作开发规范迁移到新项目，或者在一个已经稳定的项目里做二次优化。

大白话理解：

- 新项目刚开始：用“初始化提示词”，先搭规范骨架，不急着写业务代码。
- 项目开发一段时间后：用“二次优化提示词”，检查规范是否真的闭环，有没有规则散乱、错误日志没用起来、文档太乱等问题。

这份文档本身不是当前项目的最高优先级规则源。当前项目正式规则仍以根目录 `AGENTS.md` 和 `.cursor/*.md` 为准。

## 2. 适用对象

适合以下场景：

- 你新建了一个项目，想复用这套 Harness Engineering + 受控 Loop 的开发规范。
- 你想让 AI 在新项目里先建立规则、记忆、错误日志、任务模板，再开始业务开发。
- 你已经开发了一段时间，感觉文档、规则、任务记录、错误记录混乱，想做一次规范审计和收口。
- 你是软件测试工程师，不懂代码细节，但希望 AI 用测试视角把需求、方案、验证和风险讲清楚。

## 3. 使用前提醒

使用下面提示词前，建议先确认：

- 当前 AI 工具已经打开到目标项目根目录。
- 目标项目最好已经有基础代码或至少有明确技术栈。
- 如果是新项目，先不要让 AI 写业务功能，先让它创建规范文件。
- 如果是老项目，先让 AI 只审计，不要一上来就批量移动文件。
- 如果项目已有未提交改动，必须要求 AI 不要回滚、不覆盖、不清理用户改动。
- 如果在中国国内环境安装依赖或访问外网，必须让 AI 先说明网络风险和替代方案。

## 4. 提示词一：新项目初始化开发规范

把下面整段复制给 AI，用在新项目刚开始的时候。

```text
你现在在一个全新的项目根目录里。请先不要写业务代码，先帮我初始化一套适合 AI 协作开发的项目开发规范体系。

我的背景：
- 我在中国国内。
- 我是中国人。
- 我是软件测试工程师，不懂代码细节，但会用测试思维做 vibecoding。
- 所有规范、说明、Spec、TDD、VDD、交付总结都必须用中文大白话写，颗粒度要细，让我能看懂你为什么这么做、怎么验证、哪里有风险。

硬性规则：
1. 所有中文文档、规则、日志、源码读取和写入都必须使用 UTF-8。
2. 每次开发前必须先读取错误日志和防复发日志。
3. 每次发生命令失败、构建失败、接口异常、页面报错、验证失败、环境阻塞、规则执行偏差，都必须第一时间写入错误日志。
4. 非小修小改任务必须有 Spec/SDD、TDD、VDD。
5. Spec/SDD、TDD、VDD 必须模板化，包含标题、背景、范围、非范围、方法/方案、验证内容、失败场景、是否通过验证、残余风险。
6. AI 可以在已确认范围内做实现细节决策，但不能替我决定需求范围扩大、契约变化、风险接受、验证降级。
7. 如果任务风险较高，必须先停下来让我确认。
8. 项目规范要结合 Harness Engineering 和受控 Loop 思路：允许 AI 自动推进，但必须有范围、验证、暂停条件、错误记录和交付证据。
9. 如果项目已有未提交改动，不能回滚、覆盖或清理用户改动，除非我明确要求。
10. 如果需要联网、安装依赖、升级依赖、迁移数据库或执行破坏性命令，必须先说明风险和替代方案。

请你完成以下事情：

一、先审计当前项目
- 读取项目根目录文件。
- 判断技术栈、前端目录、后端目录、测试目录、配置目录、文档目录。
- 判断是否已有 AGENTS.md、.cursor、docs、README、脚本目录。
- 判断当前是否存在未提交改动或用户已有文件。
- 不要改业务代码。

二、创建或优化这些规范文件
请根据当前项目实际情况创建或更新：

- AGENTS.md
  - 作为项目总入口规则。
  - 写清楚读取顺序、规则优先级、开发流程、错误日志规则、文档回写规则、验证命令入口。

- .cursor/prompt.md
  - 作为项目初始化提示词和规则总说明。
  - 写清楚我是测试工程师、需要中文大白话、UTF-8、Spec/TDD/VDD、错误日志优先。

- .cursor/workflow_rules.md
  - 写清楚默认开发流程：Spec/SDD -> TDD -> Execution -> VDD。
  - 写清楚什么时候必须等我确认。
  - 写清楚小修小改和非小修小改的区别。

- .cursor/autonomy_rules.md
  - 定义 AI 自治等级 L0-L4。
  - L0/L4 只能审计、解释、提方案，不能直接实现。
  - L3 必须写 Loop 合同。
  - AI 不能替我接受风险或扩大范围。

- .cursor/loop_rules.md
  - 定义受控 Loop 的启动条件、循环次数、验证条件、暂停条件、错误记录方式。
  - 每轮 Loop 必须有记录。

- .cursor/architecture.md
  - 根据当前项目技术栈写架构红线。
  - 明确前端请求入口、后端路由入口、配置入口、AI 能力入口、日志入口等边界。

- .cursor/storage_rules.md
  - 写清楚配置、密钥、环境变量、文件上传、日志、缓存、数据库等存储边界。

- .cursor/project_rules.md
  - 写当前项目特有规则。
  - 包含命名、目录、验证命令、禁止事项、文档规范。

三、创建 docs 项目记忆体系
创建：

- docs/README.md
  - 作为 docs 文档索引。
  - 说明各目录用途。

- docs/project-memory/error_event_log.md
  - 错误事件日志。
  - 每次错误第一时间写入这里。

- docs/project-memory/error_prevention_log.md
  - 防复发手册。
  - 只记录已经证明会重复出现的错误模式。

- docs/project-memory/current_phase.md
  - 当前阶段事实。

- docs/project-memory/decision_log.md
  - 已确认的重要决策。

- docs/project-memory/module_memory.md
  - 模块级记忆。

- docs/project-memory/task_handoff.md
  - 最近任务交接。

- docs/project-memory/development_checklist.md
  - 每次开发前短清单。

- docs/project-memory/loop_run_log.md
  - 受控 Loop 执行记录。

- docs/project-memory/dialogue_bootstrap.md
  - 新对话快速启动摘要。

四、创建任务模板
创建：

- docs/task-templates/README.md
- docs/task-templates/spec-sdd-template.md
- docs/task-templates/tdd-template.md
- docs/task-templates/vdd-template.md
- docs/task-templates/loop-contract-template.md

模板必须是中文大白话，字段要细，适合不懂代码的软件测试工程师理解。

五、创建任务目录规则
创建：

- docs/tasks/README.md

说明每个非小修小改任务都放到：

docs/tasks/YYYY-MM-DD-任务名/

里面至少包含：

- spec-sdd.md
- tdd.md
- vdd.md

六、可选创建规则检查脚本
如果项目适合，请创建 scripts/rule_check.ps1 或等价脚本，用于检查最基本的 P0 红线。

脚本要求：
- 兼容 Windows PowerShell。
- 输出尽量使用 ASCII，避免中文编码问题。
- 不要误报太多。
- 不要修改文件，只检查。

七、最后输出
请最后给我：
1. 你创建/修改了哪些文件。
2. 当前项目开发规范读取顺序。
3. 以后每次开发 AI 必须遵守的硬规则。
4. 我作为测试工程师，下一次提需求时应该怎么说，才能触发 Spec/TDD/VDD 流程。
5. 哪些地方还需要等项目稳定后做二次优化。
6. 本次没有改动哪些业务代码或高风险文件。
7. 哪些验证已经执行，哪些验证没执行，没执行的原因是什么。
```

## 5. 提示词二：项目稳定后二次优化

把下面整段复制给 AI，用在项目已经开发了一段时间、文件和业务结构基本稳定以后。

```text
当前项目已经开发了一段时间，文件、目录、业务模块、前后端结构基本稳定。请你帮我对现有 AI 开发规范体系做一次二次优化。

注意：
- 先不要改业务代码。
- 先读取 AGENTS.md、.cursor/*.md、docs/project-memory/*.md、docs/task-templates/*.md。
- 读取中文文件必须使用 UTF-8。
- 开发前必须先读取 error_event_log.md 和 error_prevention_log.md。
- 如果过程中任何命令失败或验证失败，必须第一时间写入 error_event_log.md。
- 如果项目已有未提交改动，不能回滚、覆盖或清理用户改动，除非我明确要求。

我的背景：
- 我是中国国内的软件测试工程师。
- 我不懂代码实现细节，但会用测试思维判断需求、风险、验收。
- 所有输出必须中文大白话，颗粒度详细。
- Spec/SDD、TDD、VDD 必须让我能看懂，不要只写技术结论。

这次目标：
请审计当前项目的开发规范是否已经闭环，重点检查有没有这些问题：

1. 入口是否清晰
- 新 AI 进入项目后，是否知道第一步读哪个文件。
- AGENTS.md 是否过大、过乱。
- .cursor/prompt.md 是否还承担了太多职责。
- docs/project-memory/dialogue_bootstrap.md 是否可以作为 30 秒快速启动摘要。

2. 规则是否分层
检查这些内容有没有混在一起：
- 长期硬规则
- 当前阶段事实
- 历史任务记录
- 错误日志
- 防复发规则
- 模块局部记忆
- 任务交接
- 对话启动摘要

如果混乱，请给出拆分和移动方案。

3. 错误日志闭环是否有效
检查：
- 是否明确要求开发前读取 error_event_log.md。
- 是否明确要求任何错误第一时间写入 error_event_log.md。
- 是否明确任务结束时判断是否升级到 error_prevention_log.md。
- error_event_log.md 是否变成流水账。
- error_prevention_log.md 是否真的包含根因、防复发规则、最低验证动作。

4. Spec/TDD/VDD 是否适合我
检查：
- 模板是否足够大白话。
- 是否有标题、背景、范围、非范围、方法/方案、测试目标、验证场景、失败场景、验证证据、是否通过、未验证项、残余风险。
- 是否能限制 AI 不要写太散。
- 是否能让我用测试思维审需求和验收。

5. Harness Engineering + Loop 是否结合得合理
请审计：
- AI 自治等级是否清楚。
- L0-L4 是否能限制风险。
- L3 受控 Loop 是否有 Loop 合同。
- Loop 是否有最大轮次、暂停条件、验证目标、错误记录。
- AI 是否被禁止擅自扩大范围、修改契约、降低验证。
- 是否避免了“只告诉最终效果，过程全交给 AI 黑箱决策”的风险。

6. 文档目录是否清晰
检查 docs 是否需要分类，例如：
- overview
- architecture
- ai
- api
- api-automation
- guides
- operations
- planning
- project-memory
- task-templates
- tasks

如果当前 docs 根目录有很多 Markdown，请提出整理方案。

7. 项目规则是否和真实代码匹配
请根据当前项目实际技术栈检查：
- 前端请求入口是否明确。
- 后端接口入口是否明确。
- 配置、密钥、环境变量是否有统一规则。
- AI 调用、Prompt 配置、模型配置是否有统一入口。
- 日志、异步任务、WebSocket、测试执行器等高风险链路是否有红线。

8. 自动化检查是否合理
检查 rule_check.ps1 或现有检查脚本：
- 是否能跑。
- 是否误报太多。
- 是否覆盖 P0 红线。
- 是否兼容 Windows PowerShell。
- 是否输出清楚。
- 是否需要新增文档路径检查、旧路径残留检查、尾随空白检查。

9. 国内开发环境是否考虑到了
检查：
- 依赖安装是否可能受网络影响。
- 是否应该优先使用锁文件、已有依赖、国内镜像或离线方案。
- 是否避免了为了“能跑起来”而降低安全配置。
- 是否把环境问题和代码问题区分清楚。

10. 高风险操作是否有闸门
检查：
- 数据库迁移、删除数据、批量移动文件、依赖大版本升级、认证鉴权、生产配置、安全策略等操作，是否必须先让我确认。
- AI 是否明确不能擅自执行破坏性命令。

请按以下方式工作：

第一步：只审计，不修改
输出：
- 当前规范体系现状。
- 已经做得好的地方。
- 不闭环的地方。
- 风险点。
- 优化方案。
- 哪些文件要改。
- 哪些文件不要动。
- 是否需要我确认。

第二步：等我确认后再修改
如果我说“可以”或“开始”，你再执行文件修改。

第三步：修改后必须验证
至少验证：
- 规则文件能被正常读取。
- Markdown 路径没有明显缺失。
- docs 根目录是否符合分类规则。
- rule_check.ps1 或等价脚本是否能运行。
- git diff --check 是否通过。
- 本轮错误是否写入 error_event_log.md。
- VDD 是否记录验证结果。

最后交付：
请给我一份中文大白话总结：
1. 这次优化了什么。
2. 为什么这样优化。
3. 现在新 AI 进入项目应该按什么顺序读取。
4. 哪些事情 AI 可以自己决定。
5. 哪些事情必须问我。
6. 错误发生后怎么记录。
7. Spec/TDD/VDD 怎么写。
8. Loop 怎么启动、怎么停、怎么验收。
9. 还剩哪些风险。
```

## 6. 复用时的遗漏检查清单

复制到新项目后，让 AI 自查下面这些点。全部通过后，才算迁移得比较稳。

| 检查项 | 为什么要查 | 通过标准 |
| --- | --- | --- |
| 入口文件 | 防止新 AI 不知道先读什么 | 根目录有 `AGENTS.md`，里面写清读取顺序 |
| 初始化提示词 | 防止规则散在聊天记录里 | 有 `.cursor/prompt.md` |
| 流程规则 | 防止 AI 直接写代码 | 有 `.cursor/workflow_rules.md`，明确 `Spec/SDD -> TDD -> Execution -> VDD` |
| 自治等级 | 防止 AI 黑箱决策 | 有 `.cursor/autonomy_rules.md`，明确 L0-L4 |
| Loop 规则 | 防止无限循环或越界修改 | 有 `.cursor/loop_rules.md` 和 Loop 合同模板 |
| 架构红线 | 防止 AI 绕开项目结构乱写 | 有 `.cursor/architecture.md`，并且和真实技术栈匹配 |
| 存储规则 | 防止配置、密钥、文件、日志乱放 | 有 `.cursor/storage_rules.md` |
| 项目特有规则 | 防止只套模板不贴合项目 | 有 `.cursor/project_rules.md` |
| 错误事件日志 | 防止错误发生后只在聊天里飘过 | 有 `docs/project-memory/error_event_log.md` |
| 防复发手册 | 防止重复踩同一个坑 | 有 `docs/project-memory/error_prevention_log.md` |
| 开发前清单 | 防止每轮都忘读规则 | 有 `docs/project-memory/development_checklist.md` |
| 任务模板 | 防止 Spec/TDD/VDD 写得太散 | 有 `docs/task-templates/*.md` |
| 任务目录 | 防止过程文档散落 | 有 `docs/tasks/README.md` |
| 文档索引 | 防止 docs 变成垃圾堆 | 有 `docs/README.md` |
| 任务交接 | 防止换会话断上下文 | 有 `docs/project-memory/task_handoff.md` |
| 启动摘要 | 防止新会话读取成本太高 | 有 `docs/project-memory/dialogue_bootstrap.md` |
| UTF-8 规则 | 防止中文乱码 | 入口规则明确要求 UTF-8 读写 |
| 用户画像 | 防止输出太技术化 | 明确“中文大白话、软件测试工程师视角” |
| 中国国内环境 | 防止依赖和网络误判 | 明确依赖安装、联网访问、镜像、锁文件策略 |
| 未提交改动保护 | 防止 AI 回滚用户文件 | 明确禁止擅自 revert、reset、覆盖用户改动 |
| 高风险闸门 | 防止 AI 自作主张 | 数据库、依赖升级、认证、安全、删除、批量迁移必须确认 |
| 验证证据 | 防止只说“应该没问题” | VDD 记录命令、结果、未验证项和残余风险 |

## 7. 我检查后补上的点

相比最初两段提示词，我额外补了这些容易遗漏的规则：

1. 未提交改动保护：AI 不能擅自回滚、覆盖、清理已有改动。
2. 中国国内环境：依赖安装、联网访问、镜像和锁文件策略需要提前说明。
3. 高风险操作闸门：数据库迁移、删除、批量移动、依赖升级、安全配置必须先确认。
4. 环境问题和代码问题分离：不能因为本地没启动服务就误改代码。
5. 验证证据要求：交付时必须写清楚跑了什么、结果是什么、没跑什么。
6. 文档目录治理：新项目一开始就要避免所有 Markdown 堆在 `docs` 根目录。
7. Loop 停止条件：不能只说允许 AI 循环，还要有最大轮次、暂停条件和验收条件。
8. 防复发升级判断：错误日志不是终点，重复错误要沉淀到防复发手册。

## 8. 快速使用建议

如果是全新项目，推荐顺序：

1. 复制“提示词一”给 AI。
2. 等 AI 创建规范文件。
3. 让 AI 交付读取顺序和硬规则。
4. 再开始第一个业务需求。

如果是老项目，推荐顺序：
