# TestHub 开发流程补充规则

## 1. 文件职责

本文件属于 B 层“项目规则”，用于定义当前仓库的：

- 任务分级方式
- 确认闸门
- 最低验证标准
- `Spec/SDD`、`TDD`、`VDD` 文档表达口径
- 受控自治与 Loop 入口
- 错误记录闸门
- 文档回写规则

本文件不负责定义架构红线；如与 `architecture.md` 冲突，以 `architecture.md` 为准。

## 2. 默认流程

当前仓库默认沿用全局标准流程：

1. `Spec/SDD`
2. `TDD`
3. `Execution`
4. `VDD`

开始正式修改前，至少要明确：

- 当前生效规则
- 本轮自治等级 L0-L4
- 是否允许受控 Loop
- 范围边界
- 验收标准
- 验证目标与失败场景

受控自治与 Loop 规则：

- 每轮任务必须先按 `.cursor/autonomy_rules.md` 判断自治等级
- L0 / L4 只能审计、解释、提方案和等待用户确认，不能直接实现
- L3 受控 Loop 必须遵守 `.cursor/loop_rules.md`，并在 `docs/project-memory/loop_run_log.md` 留痕
- AI 可以决定已确认范围内的实现细节，不能决定范围扩大、契约变化、风险接受或验证降级

## 3. 任务分级表

| 触发条件 | 任务等级 | 必须动作 |
| --- | --- | --- |
| 同时改前端和后端 | 高风险 | 先走完整 `Spec/SDD`，等待用户确认 |
| 改接口字段、返回结构、route meta 或导航真源 | 高风险 | 明确兼容面、回归面、最低验证 |
| 改数据模型、迁移或对象状态流转 | 高风险 | 明确状态、结果、日志和前端展示影响 |
| 改登录、JWT、权限、执行器、异步任务、通知、报告、WebSocket | 高风险 | 必须视为非“小修小改” |
| 改 AI 配置入口、模型调用链、统一 AI 服务接入方式 | 高风险 | 必须先走 `Spec/SDD` |
| 改 `frontend/src/utils/api.js`、路由守卫、Pinia 用户/鉴权相关 store | 高风险 | 必须先走 `Spec/SDD` |
| 需求存在不确定、歧义、取舍问题 | 高风险 | 先提问，禁止自行决定后继续推进 |
| 单文件或最多两个相邻文件的小型文案、样式或局部兼容修正，且不触发上述任一项 | 小修小改 | 可走快速路径，但仍需给出最小 `Spec/TDD/VDD` |

## 4. Spec 确认闸门

### 4.1 必须等待用户确认的场景

- 新功能
- 跨模块改动
- 高风险链路改动
- 接口协议变化
- 数据模型变化
- AI 接入方式变化
- 任何会影响实现、验收或回退的歧义场景

### 4.2 快速路径适用条件

仅当以下条件全部满足时，才可按“小修小改”快速推进：

- 主要改动集中在单一文件，顺带改动不超过 1 个相邻文件
- 不涉及跨模块联动
- 不改接口协议、数据模型和迁移
- 不触发登录、权限、执行器、异步任务、通知、报告、WebSocket、AI 配置或模型调用链
- 不改 `frontend/src/utils/api.js`、路由守卫、Pinia 用户/鉴权相关 store
- 能通过 1 到 2 条命令或 1 个页面操作完成验证

只要任一条件不满足，就必须回到标准路径和确认闸门。

## 4.3 大白话与细颗粒度要求

`Spec/SDD`、`TDD`、`VDD` 和需求确认内容必须按以下口径编写：

- 必须使用中文大白话，避免只给技术术语和抽象结论
- 必须面向不写代码的软件测试工程师说明，让用户能判断需求、风险、验收和异常场景
- 必须写清“本轮要解决什么、明确不做什么、用户能看到什么变化、怎么验收、失败时是什么样子、如何回退或止损”
- 技术名词、接口名、字段名、路径和库名可以保留英文原文，但必须补充业务含义或测试视角解释
- 需求确认不能只写“按常规实现”“优化体验”“修复问题”，必须拆成可检查的行为点和验收点
- 如果存在多种方案、范围取舍或风险接受，必须暂停让用户确认，不能替用户决定

## 4.4 模板化与落盘要求

非“小修小改”任务必须按 `docs/task-templates/` 生成任务文档，并默认落盘到：

```text
docs/tasks/YYYY-MM-DD-任务名/
```

默认文件名：

- `spec-sdd.md`
- `tdd.md`
- `vdd.md`

模板使用规则：

- `Spec/SDD` 必须包含标题、背景、目标、不做范围、范围边界、已知事实、方案说明、待确认项、风险回退和验收标准
- `TDD` 必须包含测试目标、测试范围、测试数据、主流程用例、异常边界用例、回归检查、验证命令和失败判定
- `VDD` 必须包含改动摘要、验收核对、验证执行记录、错误事件、未验证项、残余风险、回退止损和最终结论
- 不允许输出只有一两段概括的空泛 `Spec/TDD/VDD`
- 不允许省略“不做范围”“失败判定”“未验证项”“残余风险”
- 小修小改若不落盘，也必须在对话中按同样字段给出最小版说明

## 5. 最低验证表

| 改动类型 | 最低验证 |
| --- | --- |
| 后端普通改动 | 至少做导入级、编译级、调用级或 `pytest` 级验证 |
| 后端接口字段、权限、过滤、排序、分页、返回结构改动 | 至少核对一次真实请求响应 |
| 前端普通改动 | 至少做构建级、类型级或受影响页面验证 |
| 前端关键交互改动 | 至少覆盖一次主流程和一次异常流程 |
| 导航、页面壳、route meta、全局状态、接口封装改动 | 必须说明回归面 |
| 前后端联动改动 | 至少核对请求参数、响应结构、页面展示三者一致 |
| 高风险链路改动 | 必须说明状态、结果、日志和前端展示四个面的影响与验证方式 |

交付时必须标注验证可信度等级：

- V0：未验证
- V1：静态验证
- V2：构建验证
- V3：行为验证
- V4：回归验证

验证等级定义以 `.cursor/loop_rules.md` 为准。未达到更高等级时，必须用大白话说明原因和残余风险。

## 5.1 Git 与 GitHub 提交规则

当用户明确要求提交 Git 或推送 GitHub 时，必须遵守：

- 提交前先确认当前分支、远程地址和暂存范围，并明确排除临时产物、诊断输出、构建产物等不应提交的文件。
- `commit message` 必须使用中文总结当前提交内容，标题要能让用户一眼看懂本次提交解决了什么或交付了什么。
- 禁止只写 `update`、`fix`、`chore`、`wip`、`提交代码` 这类无法表达提交范围的空泛信息。
- 如果一次提交包含多个阶段成果，应在提交信息中体现主线范围，例如“完成 P0.1 前后端基线、文档规范与启动体验修复”。
- 推送前至少执行暂存区格式检查或等价检查；如果因为环境限制无法验证，必须在交付说明里写清楚。

## 6. 修 Bug / 小优化防回归清单

当任务目标是“修 bug、修兼容、体验小优化”时，在进入 `Execution` 前必须显式说明：

- 本次相关边界值：空值、缺省值、极值、长文本、分页边界、重复提交等
- 本次回归面：受影响的旧入口、旧接口、旧字段、旧页面、旧数据
- 本次周边模块影响：状态流转、权限判断、缓存刷新、异步任务、日志、通知、报告等副作用
- 本次是否需要回退或止损方案

若上述任一项不清楚，必须先回到 `Spec/SDD` 提问澄清。

## 7. 错误记录闸门

### 7.1 开发前读取

进入任何开发任务前，必须先读取：

- `docs/project-memory/error_event_log.md`
- `docs/project-memory/error_prevention_log.md`

读取后需要确认本轮任务是否命中既有错误事件、错误模式或防复发规则。

### 7.2 开发中记录

开发中遇到以下任一情况，必须第一时间写入 `docs/project-memory/error_event_log.md`：

- 命令失败
- 构建失败
- 编译失败
- 测试失败
- 接口异常
- 页面报错
- 控制台红错
- 验证失败
- 环境阻塞
- 规则执行偏差

错误事件日志只要求记录现场、影响范围、临时处理和当前状态，不要求当场完成根因分析。

### 7.3 收尾升级判断

任务收尾时必须回看本轮新增错误事件，并判断是否需要升级到 `docs/project-memory/error_prevention_log.md`。

满足以下任一条件时，必须升级沉淀：

- 同类错误第二次出现
- 已经确认根因
- 已经能形成稳定防复发规则
- 错误影响高风险链路、验证可信度或后续开发口径

升级后，应在 `error_event_log.md` 中标记“已沉淀”。

## 8. 文档回写表

| 变化类型 | 必须回写的位置 |
| --- | --- |
| 长期规则变化 | `.cursor/*.md` 或对应子目录 `AGENTS.md` |
| 阶段边界、验收口径、下一步主线变化 | `docs/project-memory/current_phase.md` |
| 已确认的关键取舍、冻结口径、不可回退决策 | `docs/project-memory/decision_log.md` |
| 模块级边界、局部风险、开发注意事项变化 | `docs/project-memory/module_memory.md` |
| 一轮任务完成后的最近进展、未完成项、阻塞项与下一步建议 | `docs/project-memory/task_handoff.md` |
| 非“小修小改”任务的 `Spec/SDD`、`TDD`、`VDD` | `docs/tasks/YYYY-MM-DD-任务名/` |
| L3 受控 Loop 的执行过程、循环次数、验证证据与暂停原因 | `docs/project-memory/loop_run_log.md` |
| 任意错误现场、命令失败、构建失败、接口异常、页面报错、控制台红错、验证失败、环境阻塞或规则执行偏差 | `docs/project-memory/error_event_log.md` |
| 已证明会重复出现的错误模式、根因分析、防复发规则与最低验证动作 | `docs/project-memory/error_prevention_log.md` |
| 对话启动摘要变化 | `docs/project-memory/dialogue_bootstrap.md` |
| 显著规则、功能或文档变更 | `更新日志.md` |

## 9. 记忆回写规则

完成以下任一场景后，除更新日志外，至少还应回写一份 `docs/project-memory/*.md`：

- 冻结新的阶段边界、验收口径或下一步主线
- 确认新的架构取舍、对象边界、流程口径或兼容策略
- 明确某个模块的局部红线、局部风险或高频开发注意事项
- 本轮任务做到一半需要暂停，必须给下一轮留下清晰交接入口
- 修复会改变后续实现口径的重要 bug 或兼容问题
- 本轮出现错误事件、验证失败或环境阻塞
- 同类错误第二次出现，或已经可以稳定归纳出可复用的防复发规则与最低验证动作

默认映射关系如下：

- 阶段变化：`current_phase.md`
- 决策冻结：`decision_log.md`
- 模块经验：`module_memory.md`
- 任务过程文档：`docs/tasks/YYYY-MM-DD-任务名/`
- 本轮收尾与交接：`task_handoff.md`
- 受控 Loop 留痕：`loop_run_log.md`
- 错误事件现场：`error_event_log.md`
- 错误模式沉淀：`error_prevention_log.md`
- 新会话启动摘要：`dialogue_bootstrap.md`
