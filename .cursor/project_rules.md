# TestHub 技术栈与项目实现细则

## 1. 文件职责

本文件属于 B 层“项目规则”，用于定义当前仓库长期有效的：

- 代码风格
- 命名习惯
- 注释策略
- 接口兼容策略
- 页面范式
- 交付底线

## 2. 后端代码风格

- Python 文件名、模块名、函数名、变量名优先使用 `snake_case`
- Django / DRF 入口优先保持短小清晰，复杂逻辑下沉
- 新增日志优先进入现有日志体系，不到处散写 `print`
- 新增字段、模型和序列化逻辑时，优先复用现有 app 的组织方式

## 3. 前端代码风格

- Vue 页面和组件优先沿用当前单文件组件写法
- 页面级逻辑留在页面内，共享逻辑再考虑提取到 `stores`、`components` 或 `utils`
- 与后端交互统一通过 `frontend/src/api/*`
- 长列表页、长表单页和结果页必须显式检查滚动容器、内容截断和主内容区展示，不依赖浏览器默认行为碰运气
- 前端 Excel 导出统一通过 `frontend/src/utils/excelExport.js`，禁止新增或恢复 `xlsx` 依赖

## 4. 命名与结构

- Django app 保持按业务域拆分，如 `projects`、`testcases`、`requirement_analysis`、`ui_automation`、`app_automation`
- 前端页面目录与业务域尽量对应，便于从页面反查接口和后端模块
- 新增 API 封装函数名应尽量与后端语义一致，避免过度抽象命名

## 5. 接口与字段兼容策略

- 新增或修改接口时，优先保持所在模块既有返回结构和错误风格
- 页面字段名优先与后端语义一致；如需适配，优先在前端 API 层或页面适配层处理
- 若修改公共字段、route meta、认证字段、来源标签、处理状态等共享语义，必须同步检查消费端和相关文档
- 拆分或新增用户可见子模块时，必须同步导航真源、路由、route meta、Dashboard 快捷入口、i18n 文案和相关文档；旧入口只能作为隐藏重定向兼容保留，不能继续作为侧边栏或 Dashboard 可见入口

## 6. 页面范式

推荐遵循以下页面职责：

- 列表页：负责筛选、分页、批量操作和列表态展示，不膨胀为复杂对象编排中心
- 详情页：负责对象主信息、摘要、入口和轻量关联展示
- 编辑页：负责输入、校验、提交和必要的上下文回填
- 结果批次页：负责结果对象、处理状态和批量动作，不伪装为任务对象主页面
- 前端样式 UI 一致化：所有包含搜索/筛选区、操作按钮和数据表格的页面，其搜索/筛选组件、操作按钮的排版、对齐方式、位置及样式必须与平台已有的标准页面（如 ProjectManagement.vue）保持完全一致。统一采用标准的网格系统对齐（如 el-row :gutter=16/18），放置在列表表格上方、页面主壳（或 ListShell）中，保持一致的间距与布局顺序，不得随意设计新布局。具体组件级与代码级开发范本可参考规范文档 [unified-table-template-spec.md](file:///e:/testhub_platform-main/testhub_platform-main/docs/architecture/unified-table-template-spec.md)。
- 列表筛选区统一进入 `ListShell #filters` 插槽，筛选控件必须撑满所在列宽，禁止落入默认内容区或再包一层卡片。

## 7. 编码与中文规则

- 所有规则文件、文档文件和源码文件统一使用 UTF-8
- 读取中文规则、文档、日志和源码时，必须显式使用 UTF-8 或确认工具默认按 UTF-8 处理；PowerShell 优先使用 `Get-Content -Encoding UTF8`
- 与用户沟通、规范文档、设计文档、交付说明统一使用中文
- 用户默认是中国国内的软件测试工程师，不要求能读懂代码；需求确认、`Spec/SDD`、`TDD`、`VDD` 和交付说明必须使用中文大白话、细颗粒度表达
- 国内网络环境下，不为单次任务随意新增外部依赖、外部服务或需要稳定访问境外资源的方案；确需新增时必须先说明原因、替代方案和验证方式，并等待确认
- 所有新增或修改的代码注释统一使用中文；字段名、协议关键字、库名、框架名和第三方服务名可保留英文原文
- 遇到中文乱码时，先判断是文件编码问题还是终端输出问题，再决定是否修复源文件

## 8. 注释策略

- 不强制“写代码必须写注释”；禁止为了凑注释而写显而易见的描述性注释，例如“获取列表”“设置变量”“返回结果”
- 当出现以下任一场景时，必须补充中文注释，说明“为什么 / 约束 / 取舍 / 不能改什么”
- 非直观业务规则或边界条件，例如默认值、特殊校验、异常分支为何如此处理
- 兼容性与历史包袱，例如旧接口、旧数据、旧行为的兼容原因与风险
- 性能、安全、一致性取舍，例如为何不用更直观写法、为何要缓存、限制或降级
- 明显副作用或高风险点，例如会触发异步任务、通知、报告、状态流转或缓存刷新
- 注释语言要求沿用 7 节：注释用中文，关键字、库名和第三方服务名可保留英文原文

## 9. 验证与交付底线

- Python 改动至少做导入级、编译级、调用级或测试级验证
- 前端改动至少做构建级、类型级或页面级验证
- 高风险改动必须说明改了什么、为什么安全、验证了什么、还剩什么未验证项
- 每次完成显著功能、规则或文档变更后，应同步更新 `更新日志.md`

## 10. 明确禁止

- 为了统一风格把老代码一次性重构成完全不同的体系
- 在前端复制后端业务规则，在后端复制前端展示规则
- 未经验证就调整登录、token、动态路由、执行器、异步任务、报告或 AI 调用链
- 继续引入 `xlsx` 或在文档模板中保留 `XLSX` 示例
- 在页面、store、api 拦截器中直接使用 `window.location.reload()` 或浏览器跳转兜底平台导航
